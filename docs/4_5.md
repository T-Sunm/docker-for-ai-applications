
Compose in the Docker ecosystem
When I started my work with Docker, I quickly realized that it is hard to connect and manage many containers together. Keep it clear and manageable, difficult. Scale, forget about it. I needed something that makes this work easy and quick, and I found Docker Compose. Docker Compose is a container orchestration tool. It allows us to describe the whole application with all of needed components, networks, volumes, behaviors, and so on, in one single YAML file. Docker is more than just the tool to run containers. It is a whole ecosystem, images under creation, registries, CLI, tools like Docker Desktop, for example. example. Compose is in the middle. It allows us to connect all components into one working application. The standard workflow is very simple. We create the YAML file with the definition of our application, where the images are, how the containers are configured, what networks and ports are used. The connections and dependencies between containers are described there as well. Then we run docker-compose-app and run the stack. This allows developers to easily manage the infrastructure without bothering with the deep system-related administration. We can focus on the development. Later, when we run the application in a production environment, like Kubernetes for example, We will already know how the application behaves and we'll see using Compose is relatively similar to the feel of an application on production. When we use containers and we work in local environments, Compose might be our best friend.

Configuration as Code basics
Imagine this, we are tasked with creating a complex infrastructure and application. There are storages, databases, front-end and back-end servers. And we're doing all by hand. Every single server, every setting, every user, their permissions, applications, all by hand. Sounds like a nightmare. That's why we have configuration as code. Configuration as code let us treat infrastructure in the same way as we treat application. This means that we have code which can and should be versioned, reviewable, centrally deployable, and repeatable. This brings control, consistency, reduces errors, and enables collaboration. To make sure that we really understand configuration as code, let's go through its principles. Declarative. The code describes the desired state of the system. We do not say how something should be done, installed, configured, and so on. We say what state this component should have. Translating into human language. We don't say go to the kitchen, get the bread, use cheese and so on. We say I want three sandwiches with cheese. The tool's internals know how to make the sandwich. Idempotent. Second important concept. It means that when we run the same configuration against the same server it doesn't change anything. No action is taken. The tool checks the state, compares with desired state, and if no change is needed, no action is taken. Finally, immutability. This principle defines that if we change anything in configuration of the resource, the resource must be created as new. These three are most important. Of course, we have a few more, like the code must be versioned. This allows us to track the changes, review them, and reverse if needed. The code must be repeatable. We should be able to run the configuration against many instances with exactly the same results. Automation, readability, testability are the core principles here too.
